A battery pack, a hydrogen electrolyser and a powered prosthetic hand all depend on control software. It has to estimate what cannot be measured directly, such as how full and how worn a battery is, keep the device inside safe limits, and act on faults. The five repositories here let you run that kind of software against a model on your own computer, before any hardware exists.

Three are battery management system (BMS) simulators for electric scooters, retrofitted cars and buses. They ship a Python package called bms, run with the same command (python -m bms.simulation), pass 112 tests and print the same validation figures. The fourth simulates the controller of a PEM, AEM or alkaline electrolyser. The fifth decodes muscle signals (EMG) into prosthetic-hand commands. The guides write for students, engineers, e-mobility and energy analysts, and makers, and for non-programmers who want an AI assistant to explain each part.

## The five tools

### 1. cell-guardian: a battery management system with eight chemistries

cell-guardian simulates a battery pack the way a BMS controller would manage it. An Extended Kalman Filter estimates state of charge from voltage and current over a 2-RC Thevenin cell model. A separate estimator tracks state of health as capacity and resistance fade. A supervisor opens the contactors on over-voltage, under-voltage, over-current, over-temperature and isolation faults. Balancing, thermal control and power limits are included.

It ships presets for an electric scooter (15S LFP), a lead-acid 4W retrofit, a modern LFP 4W and an electric bus, and 8 cell chemistries including LFP, NMC, Na-ion and LTO. It generates its own battery datasets in the Kaggle file layouts, so analysis code written now should work when you swap in the real CSVs.

The quick validation run (about 9 seconds in the guide):

python -m bms.simulation --datasets
Main limitation. Its validation data are synthetic, generated by the package’s own cell model, so the very low errors show internal consistency only, not accuracy on real cells. It is not certified BMS firmware and must not manage a real battery. The default python -m bms.simulation run is slow (about 2 min 9 s), and its comparison table shows 1.4 kWh for the scooter while the scooter’s detail block prints 4.8 kWh (100 Ah).

Code: [github.com/herrrickshaw/cell-guardian](https://github.com/herrrickshaw/cell-guardian)

### 2. ev-battery-management-sim: the battery simulator plus NASA data cleaning

This repository has the same parts: a two-RC equivalent-circuit cell, an Extended Kalman Filter for state of charge, capacity and resistance fade for state of health, passive balancing, thermal control, power limits and a supervisor that opens the contactor on faults. Its command-line flags are --vehicle, --degradation, --cold, --driving, --manufacturers, --datasets and --plot.

It adds a notebook that turns the NASA battery .mat files into CSVs, and a validation suite for six Kaggle datasets. The degradation run for a 48 V scooter pack shows health at 90.0% at cycle 100, 80.0% at cycle 200 and 70.0% at cycle 300, with resistance rising from 2.20 to 2.60 mOhm over that span; end of life at 80% comes at about 200 cycles.

The degradation run:

python -m bms.simulation --degradation
Main limitation. The six ‘Kaggle validation’ checks run on synthetic stand-ins, and the script says so itself. Check 2 is partly circular: the fitted fade rate (0.1001 %/cycle) matches the rate used to generate the data. The NASA notebook needs a Kaggle login and download and was not run in the guide. In the distributed-BMS check, module 3 was detected as degraded (SOH 85% against 97.3%) yet the degraded-alert count stayed at 0.

Code: [github.com/herrrickshaw/ev-battery-management-sim](https://github.com/herrrickshaw/ev-battery-management-sim)

### 3. bms-battery-management: the battery simulator for a single vehicle run

This is the earliest of the three battery guides. It describes the same package: a two-RC Thevenin cell model, an Extended Kalman Filter for charge level, a wear model, passive cell balancing, thermal control, power limits and a supervisor with fault codes. It compares four vehicle classes, from a 48 V 2-wheeler LFP pack to a 409 V bus pack of 163.8 kWh.

The 2-wheeler run prints a time table of state, charge, pack voltage, current, hottest cell and fan speed. Charging started at 15.0% and reached 56.8% at 52.2 V and 47.1 C. After discharge the charge was 53.4%, with no fault and health at 99.99%.

A single 2-wheeler charge and discharge:

python -m bms.simulation --vehicle 2W
Main limitation. The ageing model is a simple linear fade, so it cannot predict the life of a specific real cell, and the validation numbers come from synthetic data. The guide found README gaps: requirements.txt omits pandas (needed by --datasets) and matplotlib (needed by --plot), and the README example uses --vehicle two_wheeler while the command line accepts 2W, 4W_RETRO or BUS. The all-vehicle plot run did not finish within two minutes. It has not been validated on a physical pack.

Code: [github.com/herrrickshaw/bms-battery-management](https://github.com/herrrickshaw/bms-battery-management)

### 4. hydrogen-electrolyser-control: a simulated electrolyser controller

This repository holds a control system for three electrolyser types (PEM, AEM and alkaline), an advanced layer with ramp profiles, data logging and safety interlocks, a Flask REST API with a Python client, and eight runnable examples. Everything runs against a software model, not a device. It needs Python 3.7 or newer with Flask, Flask-CORS, numpy and requests.

Example 5 compares the three types and prints efficiencies of 75.0% (PEM), 72.0% (AEM) and 68.0% (alkaline), which are the model’s configured maxima. Example 4 applies a power ramp: voltage saturates at 47.2 V while power keeps rising to about 4,000 W and efficiency climbs to 72.5%. The menu is interactive, so the guide pipes the choice in.

The three-type comparison, after pip install -r requirements.txt:

echo 5 | python electrolyser_examples.py
Main limitation. Simulation only, not for operating real electrolysers: the repository’s own validation notes say all testing used synthetic power profiles and no hardware testing was done. The repository is archived, so no fixes will be merged. In the guide’s runs, example 7 crashed with an AttributeError; a 45 V setpoint did not take effect (example 1 stayed at 30.0 V); and example 8 printed 316 Nm3/h of hydrogen at every power level with 0 V and 0 A, against a 0.95 Nm3/h spec in the same code. Do not quote its production numbers. The README says ‘Status: Production Ready’, which its validation notes contradict, and it names an /api/production path that the code serves as /api/monitoring/production.

Code: [github.com/herrrickshaw/hydrogen-electrolyser-control](https://github.com/herrrickshaw/hydrogen-electrolyser-control)

### 5. bionic-limb-control: EMG to prosthetic-hand commands

emg_decoder.py is a single-file reference pipeline for surface EMG from forearm muscles. It filters at 20–450 Hz with a mains notch, cuts 200 ms windows with a 50 ms step, computes the Hudgins time-domain features, classifies with StandardScaler plus LDA, smooths with a 5-window majority vote and sets proportional speed from normalised mean absolute value. It also has a two-electrode direct-control scheme (flexor closes, extensor opens, co-contraction cycles the grip) and a causal filter for streaming.

It trains on early repetitions and tests on later ones, which avoids the leakage that, per the guide, inflates accuracy by 10–20 points in many EMG projects. On its synthetic demo (8 channels, 6 classes) it reached 97.2% window accuracy offline and 88.2% agreement in a causal online replay over 500 decisions; the gap is smoothing lag at gesture changes. You can also feed it your own CSV recording with --csv.

The synthetic demo, after .venv/bin/pip install -r requirements.txt (numpy, scipy, scikit-learn):

.venv/bin/python emg_decoder.py --demo
Main limitation. Research and teaching code: not a medical device and not clinical advice. The demo data are synthetic, so 97.2% is optimistic; the README expects 75–90% on real amputee data and lower across sessions. Never attach it to a person without firmware-level current limits, end-stops and a watchdog. The README quotes 89% online agreement; the guide’s run gave 88.2%, put down to run-to-run variation. The --csv path was not run.

Code: [github.com/herrrickshaw/bionic-limb-control](https://github.com/herrrickshaw/bionic-limb-control)

## Worked example: validating the battery model with cell-guardian

This example is from the cell-guardian guide, run on 6 November 2026 on a fresh clone in a throwaway virtual environment, with no accounts or downloads. It shows the quickest way to see all four validation sections, and why the numbers need care.

Step 1: get the code and install. The repo has no requirements.txt, so the packages are named by hand.

git clone https://github.com/herrrickshaw/cell-guardian.git
cd cell-guardian
pip install numpy pandas matplotlib scipy pytest
Step 2: run the tests.

python -m pytest -q tests
112 passed in about 4 seconds (3.6 s in the guide’s stat line).

Step 3: generate synthetic datasets and validate. This prints the vehicle comparison table, six dataset shapes and a validation report, in about 9 seconds.

python -m bms.simulation --datasets
1. EKF SOC Estimation (NASA 18650 discharge cycles)
 Samples : 200
 RMSE (SOC) : 0.117 %
 MAE (SOC) : 0.113 %
 Max error : 0.182 %
 EKF final SOC : 94.4 % (true: 94.5 %)
 Verdict : PASS (target RMSE < 3 %)
2. Capacity Fade Model (Li-Ion Degradation, 300 cycles)
 SOH RMSE : 0.0504 %
 Fitted fade : 0.10010 %/cycle
 EOL prediction: cycle 199 (SOH=80 % threshold)
3. 2-RC Voltage Model (BMS v2.1 telemetry, 600 steps)
 Voltage RMSE : 1.07 mV
 Max error : 3.53 mV
4. RUL Estimation (500 cycles)
 RUL RMSE : 4.2 cycles
 EOL predicted : cycle 501
How to read it. The ‘NASA’ data here are synthetic, produced by the package’s own cell model, so a 0.117% charge error is a self-consistency check, not proof of accuracy on real cells. The same figures (0.117% charge error, 1.07 mV voltage error, 4.2 cycles of remaining-life error) appear in the ev-battery-management-sim and bms-battery-management guides. To test against real cells you would download the Kaggle datasets with download_kaggle_datasets.sh, which needs a Kaggle account; the guide did not do this.

## What these tools do not do

- None of them is ready to run real hardware. The battery simulators are not firmware; cell-guardian’s guide says it must not manage a real battery, and bms-battery-management has not been validated on a physical pack. The electrolyser code is simulation only, with no hardware testing done. Makers who connect the EMG decoder to a servo hand must add their own safety layer.

- Their validation numbers are not real-world accuracy. All three battery repos validate on synthetic data shaped like the Kaggle files. The EMG decoder’s demo data are synthetic too, and its README expects lower accuracy on real people.

- Ageing is a straight line. The battery degradation model fades 0.1% per cycle, and the script itself labels that an accelerated model, not a real LFP rate.

- They are not engineering design. Do not use them to size, cost or certify a battery pack or a hydrogen plant.

- The EMG decoder is not a medical device. It is not clinical advice, and it must not be attached to a person without independent current limits, end-stops and a watchdog in firmware.

- Some outputs are wrong. The electrolyser’s production table (example 8) is physically wrong, and that repository is archived, so it will not be fixed.
