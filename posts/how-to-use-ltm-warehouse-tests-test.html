Why it is useful

  • Who benefits: anyone maintaining scripts that write into a price or fundamentals warehouse, who wants to re-check a change instead of trusting it.
  • What it replaces: running backfill scripts against live data to see what happens.
  • Evidence from the run: all three test files passed on a throwaway Postgres 17 on port 55432, the thin-history finder flagged 4 of 7 seeded symbols, and the dry run persisted 0 rows.
  • Each seeded case encodes a real past bug: ticker already carrying a suffix, a symbol tagged under two countries, an NSE series switching mid-history.
  • The database is created and dropped by the script, even when a test fails.

What it is for

The repo verifies four maintenance scripts for an LTM (long-term) warehouse: exchange resolution (exchange_map.py), thin-history detection (find_thin_history_tickers.py), exchange-list building, and the multi-tier backfill (Yahoo, then NSE, then SerpApi estimates) in backfill_missing_history.py.

run_tests.sh creates ltm_warehouse_test, applies a schema that mirrors the real tables, seeds synthetic symbols, generates a thin_history.csv fixture, runs test_backfill_logic.py, test_backfill_cli.py and test_nse_tier.py, then drops the database.

Tests check deduplication against existing dates, routing (Yahoo into the fact table, SerpApi into a separate low-fidelity estimate table), that a dry run never persists, and that the NSE tier fires only for India and collapses series switches to one row per date.

Who it is for

  • Data engineers who maintain market-data backfills
  • Anyone who wants a pattern for throwaway-database tests with Postgres
  • Readers learning why exchange-qualified tickers matter
Not for.
  • Running against your real warehouse: the point is that it never does
  • Testing live data quality: the data is synthetic

Install

  1. Clone the repo
    git clone https://github.com/herrrickshaw/ltm-warehouse-tests.git
cd ltm-warehouse-tests
  2. Create a virtual environment and install requirements, pinning SQLAlchemy below 2.1
    python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt "sqlalchemy<2.1"
  3. Optional: start a disposable Postgres of your own on another port so nothing shared is touched
    initdb -D ./pgdata -A trust -U tester
pg_ctl -D ./pgdata -o "-p 55432 -k /tmp/pgsock" -l pg.log start

Quick start: commands and what you should see

Run the whole suite (default local Postgres)

./run_tests.sh

Creates the test database, applies the schema, seeds data, runs three test files and ends with 'All tests passed.' then drops the database.

Run against a throwaway server on port 55432

export PGPORT=55432 PGHOST=127.0.0.1 PGUSER=tester
PG_ADMIN_URL=postgresql://tester@127.0.0.1:55432/postgres ./run_tests.sh

Same output. Note that run_tests.sh builds TEST_DB as postgresql://localhost/<name> with no port, so on a non-default port you must set the PG* variables or edit that line.

Use another database name

TEST_DB_NAME=my_ltm_test ./run_tests.sh

The same flow with your name.

Limits and honest caveats

  • Not investment advice. Test data is synthetic.
  • Bug found: with requirements.txt as written (sqlalchemy>=1.4, no upper bound) a fresh install picked SQLAlchemy 2.1.5, whose default driver for postgresql:// is psycopg 3. Seeding failed with ModuleNotFoundError: No module named 'psycopg'. Installing sqlalchemy<2.1 (2.0.55) fixed it.
  • run_tests.sh hardcodes postgresql://localhost/<name> for the test database, so a server on a non-default port needs PGPORT/PGHOST set; the PG_ADMIN_URL port is not reused.
  • Postgres 17 from Homebrew also needed LC_ALL=en_US.UTF-8 for initdb and start on the test machine.
  • Observed, not investigated: in test_backfill_cli.py the dry run listed 1 row for NEWCO but the following --apply showed 0 for NEWCO.
  • Network-dependent tiers (live Yahoo, NSE, SerpApi) are not exercised; those tests use seeded data or stubs.
  • A temporary edit to run_tests.sh was made in the scratch clone for the run only; nothing was pushed.
