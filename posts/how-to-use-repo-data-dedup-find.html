Why it is useful

  • Who benefits: anyone whose GitHub LFS quota is exhausted or growing, and who needs to know which repos hold the bytes before deleting anything.
  • What it replaces: guessing from the GitHub billing page, which shows a total but not which repos duplicate each other.
  • Why it works when the quota is blown: it clones with a blob size filter, so it reads only the tiny pointer files, never the LFS objects themselves.
  • Evidence from the run: on a synthetic three-repo account it counted 1.83 GB stored against 0.71 GB unique, flagged 1.12 GB of cross-repo duplicate waste in 2 objects, and a history-only object (at_head = 0).
  • The repo also ships a dry-run-by-default script that lists archive-twin repos it would delete; the dry run was run and nothing was deleted.

What it is for

repo-data-dedup came out of a real problem: an account whose GitHub LFS budget was used up, so every LFS download failed. LFS storage is counted per repository, so a backup copy of a repo stores every large file again.

The core tool is scripts/audit_lfs.py. For every repo of an owner it makes a blobless-style clone (--filter=blob:limit=2048, no checkout), finds the LFS pointer files in the full history, and writes two CSVs: lfs_inventory.csv (every pointer, its size, and whether HEAD still references it) and repo_summary.csv (objects and bytes per repo). It then prints total stored, total unique and cross-repo duplicate waste.

The repo also holds a written playbook (audit, deduplicate, compress, eliminate LFS) and helper scripts. This post only demonstrates the audit and the safe dry run, on made-up repositories.

Who it is for

  • Developers and researchers whose GitHub account uses Git LFS across many repos
  • Anyone planning a cleanup who wants evidence of what is duplicated first
  • People who keep archive or backup copies of repos in the same account
Not for.
  • Deciding what to delete without checking: the audit counts pointers, it does not prove a copy is safe to remove
  • Accounts that do not use Git LFS (the numbers will be zero)
  • Running the destructive scripts: delete_archive_twins.sh --run deletes real repos. Read it first and run the default dry run only

Quick start: commands and what you should see

Audit your own account (read-only). Replace <owner> with your GitHub user or organisation

mkdir -p ~/lfs_audit && cd ~/lfs_audit
python3 /path/to/repo-data-dedup/scripts/audit_lfs.py <owner> ~/lfs_audit/clones

One progress line per repo, then three totals: TOTAL stored across repos, TOTAL unique content, cross-repo duplicate waste. lfs_inventory.csv and repo_summary.csv appear in the current folder.

Preview the archive-twin deletion list (dry run is the default)

./scripts/delete_archive_twins.sh

35 lines starting [dry] would delete ..., then 'Dry run only.' Nothing is deleted unless you pass --run, which needs the delete_repo scope. The list is hard-coded for the author's account; edit it before using it on yours.

Read the CSVs

column -s, -t repo_summary.csv

Per repo: visibility, status, LFS object count and bytes.

Limits and honest caveats

  • Not run on real repos for this post: all numbers above come from a synthetic account, so they show how the tool works, not any real saving.
  • Pointer sizes are what git reports; the script does not verify the objects exist on the LFS server.
  • delete_archive_twins.sh has a hard-coded list of the author's own repos and --run deletes them for real. Use the dry run only unless you have checked every name.
  • LFS storage is only freed by deleting repositories, not by deleting files; the audit cannot change that.
  • A repo with a blobless-style clone can fail on private or renamed repos; those rows show CLONE_FAILED.
