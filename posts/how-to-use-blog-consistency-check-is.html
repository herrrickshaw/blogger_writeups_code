Why it is useful

  • Who benefits: anyone who hand-writes or bulk-edits HTML blog posts with embedded CSS/JS and cannot eyeball every post after every edit.
  • What it replaces: screenshot-diff services ask whether a page changed; this asks whether it is broken, which suits posts that rarely change after publishing.
  • Evidence from the run: auditing one live post took a few seconds with only curl and node and produced a 10-rule table plus a plain-language list of failures.
  • The run found a real BLOCKER (dark palette with no light-mode lock) on a recent post, so the rules do fire on current content.

What it is for

blog-consistency-check is a checker for blog.vertistratsolution.com. It lists posts through the public Blogger feed, downloads each page with curl, and applies a fixed set of static rules. An optional Playwright pass adds computed-contrast and overflow checks in light and dark mode.

The rules encode defects that actually happened on the live blog. CHECKLIST.md explains each one, so the checklist and the code stay in step. The repo also has fix.py and helper scripts for repairing the problems; this post covers only the read-only audit.

Who it is for

  • Bloggers who publish self-contained HTML posts with their own CSS and JavaScript
  • Maintainers who bulk-edit posts with scripts and want a safety net
  • Anyone who wants a CI gate that exits non-zero on broken posts
Not for.
  • General websites: several rules are specific to this blog (WPI attribution, index link, translate widget)
  • Pixel-perfect visual regression; the repo says baseline screenshots are for eyeballing only
  • Fixing posts automatically without review; run audit.py first and read the report

Install

  1. Clone the repository.
    git clone https://github.com/herrrickshaw/blog-consistency-check.git
cd blog-consistency-check
  2. No packages are needed for the static pass. Check the two tools it shells out to.
    which curl node

Quick start: commands and what you should see

Audit one public post (static pass).

python3 audit.py --url https://blog.vertistratsolution.com/2026/10/how-to-use-ship2shorerag-offline.html

It writes out/report.md and out/report.json, prints the report path, and prints a count of BLOCKER failures. The exit code is non-zero when a blocker fails.

Read the report.

cat out/report.md

A rule-summary table (failing vs checked) followed by a list of posts needing attention, each failure tagged BLOCKER, MAJOR or MINOR.

Ways to use it

MethodHow it works
Spot-check after publishingRun --url on the new post and read the report before announcing it.
Whole-blog sweepRun python3 audit.py with no arguments to walk the full feed (about 30 seconds for the static pass per the README).
CI gateBecause blockers produce a non-zero exit, a workflow can fail when a post regresses.
Add your own ruleWrite a function in checks.py returning (ok, detail), register it in STATIC_RULES, and add a line to CHECKLIST.md.

Limits and honest caveats

  • Hard-coded to blog.vertistratsolution.com (BLOG constant in audit.py); other blogs need a code change.
  • The README's install line points at a private virtualenv path (~/.venvs/testing/bin/python3); use your own Python instead.
  • The static pass checks the HTML source, so a CSS finding like dark-vars-locked is a signal to inspect, not proof of a visible fault.
  • The --rendered pass (Playwright contrast/overflow) was not run for this post.
  • The fix scripts (fix.py, add_*.py) were not run; they edit content and need review before use. This is not investment, legal or clinical advice; it is a code-quality tool.
