Most process-safety questions start as a quick check: how big a relief valve, how much safety integrity does this scenario need, where does a gas cloud reach. This toolkit answers those at screening level from a terminal, with no software to buy and nothing to install beyond Python. It is built around the equations and standards a process-safety engineer is held to (API 520/521/526/2000, IEC 61511 and the CCPS layer-of-protection method, with the Indian OISD list as a reference), and every module says which numbers are inputs you must own.

It is a screen, not a safety case. Most of the standards are paywalled and were not read. Equations are derived from first principles where possible and unit-tested; every remaining coefficient is flagged in the module's docstring. A qualified engineer owns any result, and validated tools such as DNV Phast or RISKCURVES should decide real designs.

1. Get it running

git clone https://github.com/herrrickshaw/process-safety-design-toolkit
cd process-safety-design-toolkit
git checkout feature/ifluids-service-map   # until the two open pull requests merge
python3 -m unittest discover tests         # 173 tests should pass
python3 -m process_safety coverage         # every topic, its standards, and what is NOT implemented

The coverage command is the best first step. It lists each topic with the governing standards, the module that implements it, and an honest status. Read the “not implemented” lines before you trust anything else.

3. Run a risk study the sensible way

python3 -m process_safety qra example --out study.json     # copy the worked LPG-terminal example
python3 -m process_safety qra validate study.json          # units, sums to 1, references, data provenance
python3 -m process_safety qra hazid study.json --out hazid/   # registers for the HAZID/HAZOP workshop
python3 -m process_safety qra run study.json --sample 3 --out sample/
python3 -m process_safety qra run study.json --out qra_out/

Always run the --sample first. It runs three scenarios on a coarser grid, checks the result at double the angular resolution for convergence, and projects how long the full run will take. On the example it takes about a second and a half and writes the HAZID and HAZOP registers, an individual-risk grid, an F-N curve, building-risk and emergency-zone reports, a mitigation table and an HTML report. Open qra_report.html first.

Why sample first. The study found two bugs in itself this way: a small leak inside a bund was given the whole bund area, and a village receptor was missed because plumes went down sector centrelines only. Both were caught by checks the sample run performs, not by eye.

5. The data-centre helpers

A data centre is a high-reliability utility plant, so the same disciplines apply: power, fire, cooling water and risk. The new datacentre module covers PUE, the cooling-water heat balance, evaporative water use per kilowatt-hour of IT load (about 2.2 litres at three cycles of concentration, which matches a hand calculation), UPS battery and diesel sizing, and N, N+1 and 2N availability. It also ships a checklist of generic hazards for the fuel store, battery room, gas-suppression room, electrical rooms and cooling loops, each pointing to the toolkit module that helps.

Checked. The cooling-water flow satisfies the energy balance in both directions (double the heat doubles the flow; double the temperature rise halves it), and the water formula reproduces the 2.19 litres per kilowatt-hour hand calculation. Both are tests, not claims.
Deliberately not coded. Uptime tier availability percentages, ASHRAE temperature envelopes, and NFPA 2001 or 75 design values. The documents were not read, so the numbers would be remembered, not verified. Diesel fuel consumption has no default because it is vendor data. The availability helpers assume independent units, which overstates availability.

6. Where the toolkit stops, and what would close each gap

  • No dense-gas model. Use Phast or RISKCURVES footprints through the overrides hook, and let the toolkit do the frequencies, individual risk, ALARP and mitigation bookkeeping.
  • Paywalled standards. Reading API 752/753, IEC 60079-10-1 or IEEE 1584 would let the building-damage curves and zone extents become real code instead of inputs.
  • No Indian default criteria. No single tolerable-risk criterion exists for India in the public documents read, so the study uses UK or Dutch presets or a custom one you supply.
  • Software-class studies. Load flow, harmonics, transient stability, pulsation and illumination are listed as not implemented rather than approximated.
