Why it is useful

  • Home-lab and NAS owners who run transmission-daemon headless get a scriptable list/add/start/stop/remove tool without installing a desktop client.
  • It replaces hand-written curl calls that must juggle Transmission's X-Transmission-Session-Id CSRF header: the client catches the 409 reply, stores the id and retries automatically.
  • Developers get one TransmissionClient class shared by the CLI and the web page, which is a short, readable example of a session-token-protected JSON-RPC client.
  • Evidence from the run: against a mock daemon, list, info, add and a guarded remove all worked, and the mock log showed each call as an unauthenticated POST answered 409 followed by a retry carrying the session id.

What it is for

transmission-client talks to a transmission-daemon over its documented RPC interface. You can list torrents, show details, add a magnet link or .torrent file, start, stop and remove torrents from a terminal, a web page on 127.0.0.1:5000, or from your own Python code.

Use it only with content you have the right to download and share. The examples here use a local mock with two Linux ISO names.

Who it is for

  • People who run transmission-daemon on a server, Raspberry Pi or NAS
  • Python developers who want a compact RPC-client example
  • Scripters who want to automate adding and cleaning up torrents of legitimately shareable files
Not for.
  • Downloading or sharing copyrighted material you have no right to
  • Exposing the daemon to the internet: the README's --allowed "" setting is marked dev only
  • Replacing the official Transmission clients for day-to-day use; this client has no automated tests and a minimal feature set

Install

  1. Clone the repository
    git clone https://github.com/herrrickshaw/transmission-client.git
cd transmission-client
  2. Create a virtual environment and install
    python3 -m venv .venv
source .venv/bin/activate
pip install -e .
  3. Point it at your daemon
    export TRANSMISSION_HOST=localhost
export TRANSMISSION_PORT=9091

Quick start: commands and what you should see

List torrents

transmission-cli list

A table with ID, STATUS, DONE, SIZE, DOWN, UP and NAME columns (see sample output).

Show details for one torrent

transmission-cli info 1

Name, ID, hash, status, progress, size, speeds, ratio, peers and download directory.

Add a magnet link

transmission-cli add 'magnet:?xt=urn:btih:...'

A line like: Added: <name> (id=N).

Remove a torrent (asks first)

transmission-cli remove 3 [--delete-data] [--yes]

A prompt 'Remove the selected torrent(s)? [y/N]'. Answering anything else aborts. --yes skips the prompt.

Start the web GUI

python3 -m transmission_client.web

Serves on http://127.0.0.1:5000 with the torrent list auto-refreshing every 3 seconds. Not run in the demo; README only.

Every new process pays one extra round trip because the session id is not cached between runs.

Guarded remove with no confirmation

Remove the selected torrent(s)? [y/N]: Aborted!

With no terminal input the prompt aborts, which is the safe default.

Limits and honest caveats

  • Demonstrated against a mock daemon only. No real Transmission daemon, real torrent or network transfer was involved, so real-daemon behaviour (auth failures, large lists, RPC version differences) is untested here.
  • The web GUI was not run; only the README describes it.
  • The repo has no tests directory; the README lists no test command.
  • The session id is not cached between processes, so every CLI invocation makes two requests (visible in the mock log).
  • The remove subcommand accepts --yes but not -y.
  • The README suggests transmission-daemon --allowed "" for dev; that opens the RPC port to every host, so do not use it on an exposed machine.
  • Use only for content you are legally allowed to download and share. Not legal advice.
