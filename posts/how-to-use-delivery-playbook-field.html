Why it is useful

  • Team leads, product managers and students get one page that compares Waterfall, V-Model, Spiral, Scrum, Kanban, XP and DevOps side by side, instead of reading seven separate sources.
  • It replaces the usual 'which methodology should we use?' meeting with a two-question fit-finder: how often requirements change, and how costly a mistake is once shipped.
  • The six named failure modes (Scrummerfall, Zombie Scrum, Watermelon status, Cargo-cult DevOps, Dark agile, Spec-driven paralysis) give a team shared words for process problems, each paired with a concrete fix.
  • Evidence from the review: the committed index.html has 14 sections and 28 sub-headings, is a single file with no dependencies, and its further-reading list was link-checked by the author on 17 October 2026. This post did not run any code; it read the committed file.

What it is for

delivery-playbook is the versioned source for a reference page on how software gets delivered. It covers classic SDLC models, the Agile family, DevOps and continuous delivery, practices that hold whatever the model, a fit-finder, failure modes, an applied section, computer-science theory (Conway's Law, Little's Law, CAP theorem and others) applied to product decisions, Domain-Driven Design, TOGAF's ADM cycle and a testing playbook.

You use it by reading it in a browser, by forking the single HTML file and editing it for your own organisation, or by giving it to an AI assistant and asking questions against it.

Who it is for

  • Engineering managers and tech leads choosing or fixing a delivery process
  • Product managers and analysts who need to speak the same language as engineering
  • Students and career-changers learning how SDLC, Agile, DevOps, DDD and TOGAF relate
  • Anyone who wants a worked example of a self-contained, no-build reference page
Not for.
  • A certification syllabus: it is a field guide, not an official Scrum, SAFe or TOGAF text; the repo links the primary sources instead
  • Legal, compliance or safety-critical process sign-off
  • A runnable software library; there is no code to install

Install

  1. Clone the repository (or use Download ZIP on GitHub)
    git clone https://github.com/herrrickshaw/delivery-playbook.git
cd delivery-playbook
  2. Open the page. There is nothing to install or build.
    open index.html   # macOS; on Linux use xdg-open, on Windows double-click the file

Use the fit-finder: place your project on two axes

# In the browser, go to the 'Fit finder' section.

You land in one of four quadrants, each with a recommendation (see the sample outputs below).

The fit-finder's four recommendations (text of the Fit finder section)

(read in the browser; text copied from the section)
High stakes, known scope   -> V-Model or Waterfall. The cost of a wrong turn justifies planning it out first.
High stakes, unclear scope -> Spiral. Spend the first loops on prototypes and risk, not the full build.
Low stakes, known scope    -> Incremental or Kanban. Don't pay for ceremony the risk doesn't justify.
Low stakes, unclear scope  -> Scrum, XP, Lean Startup. Optimise for the speed of the feedback loop.

DevOps discipline runs underneath all four quadrants; it is not a fifth option.

One failure mode with its fix

(Failure modes worth naming section)
Zombie Scrum (Agile)
All four ceremonies happen, on schedule, every sprint, and nothing anyone says in them ever changes what happens next.
Fix: every retro item gets a named owner and a deadline, tracked exactly like a bug.

Sample prompts for your AI assistant

Copy, paste and edit the parts in [brackets].

  • Read index.html in this repo and summarise the six failure modes in a table: name, symptom, fix.
  • Here is how my team works: [describe]. Using the Fit finder section, which quadrant are we in and which model does the guide suggest? Tell me where our current process differs.
  • Which of the ten computer-science-theory items in this guide (Conway, Little, CAP, Amdahl and others) is most relevant to a team with long code-review queues? Quote the relevant passage.
  • Turn the testing-playbook section into a one-page checklist I can paste into a pull-request template.
  • List the primary sources linked in the further-reading section and tell me which claims in the guide each one supports.
  • Adapt this guide for a 5-person data-science team: which sections would you cut and what would you add?

Limits and honest caveats

  • No code was executed for this post: the repo is a document. Everything shown was read from the committed index.html.
  • It is a field guide with the author's opinions, not an official standard. For Scrum, TOGAF or SAFe, check the primary sources the guide links.
  • The repo's own README notes that the SAFe framework site returned HTTP 403 to the author's link check, so that source was not verified.
  • The live claude.ai copy is republished separately from this repo and the two are not auto-synced, so they can differ.
  • Fonts load from Google Fonts, so the page looks plainer offline.
  • Not legal, compliance or professional-certification advice.
