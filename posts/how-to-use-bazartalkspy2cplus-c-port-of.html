Why it is useful

  • Who benefits: engineers porting a Python research stack to C++ who want a worked example with a validation strategy, golden-fixture tests and a candid benchmark.
  • What it replaces: guessing whether a rewrite is worth it; the repo documents a measured 5.94x speedup on one pipeline and, just as usefully, the benchmarking mistake that first made C++ look 40% slower.
  • Evidence (from the repo's committed report, not re-run by me): 19 of 19 markets matched the Python original exactly, and the release build took 1.60 s against 9.52 s for Python.
  • Honest scope: the build and benchmark were not run for this post, because the dependency stack (vcpkg, DuckDB, Arrow, Drogon, librdkafka) is a long build.

What it is for

BazaarTalks-cpp is a hybrid rewrite. Libraries for the trading calendar, cross-sectional statistics, linear algebra (Eigen), storage clients (DuckDB, Cassandra, SQLite, Parquet), Kafka streaming, an HTTP client and server, and quant-core modules (risk, cost, factor, DVM scoring, backtest) are in C++. Services such as stream consumers, a serve API and a pipeline CLI sit on top.

Components with no mature C++ equivalent, such as yfinance and exchange scrapers, browser-driven data access and scikit-learn model training, stay in python-sidecar/ by design.

Each C++ module is validated against golden fixtures generated from the unmodified Python originals, with the reference command recorded in each test file's header.

I did not build the project or run the benchmark. The build needs vcpkg and heavy dependencies, and the benchmark needs the author's production data layout, which is not in the repo. Everything quantitative below is quoted from the repo's committed report and migration plan.

Install

  1. Clone the repo and bootstrap vcpkg.
    git clone https://github.com/herrrickshaw/Bazartalks_Py2Cplus.git
cd Bazartalks_Py2Cplus
git clone --depth 1 https://github.com/microsoft/vcpkg.git
./vcpkg/bootstrap-vcpkg.sh -disableMetrics
  2. Configure and build with the release preset for anything timing-sensitive.
    cmake --preset release
cmake --build --preset release
ctest --preset release

The correction that matters

docs/MIGRATION_PLAN.md, Cutover run #4
debug build (-O0, 126MB binary): bare startup ~0.28s; total C++ 12.29s vs Python 8.79s (C++ 40% slower)
release build (43MB binary):     bare startup ~0.01s; total C++  1.60s vs Python 9.52s (5.94x faster)
Accuracy: 19/19 markets exact match in both runs

The slowdown was a benchmarking bug (a debug build), not slow code. The repo records the rule: never benchmark or deploy a debug build.

Limits and honest caveats

  • Not investment advice. This is infrastructure and research code.
  • I did not build the project, run the tests or run the benchmark. All figures are quoted from the repo's committed report and migration plan (report dated 12 July 2026) and are unverified by me.
  • The benchmark data and layout are the author's own; the benchmark cannot be reproduced from the repo alone.
