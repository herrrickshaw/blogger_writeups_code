Why it is useful

  • Who benefits: SAF plant analysts, airline sustainability teams and students who want a working example of how feedstock, batches, certificates, blending and credits link together.
  • What it replaces: stitching spreadsheets across feedstock logs, batch records and credit ledgers. The data model and the calculations are already laid out and tested.
  • Evidence from the run: 39 tests passed in 3.95 seconds, the seeded database produced a dashboard summary, and one of three airports was flagged as below its mandate share.
  • It keeps the regulatory numbers in editable files, and says in the README to confirm them against the current rules before real use.

What it is for

The backend (FastAPI with SQLite) models feedstock deliveries, production batches, ASTM D7566 pathways, SAF certificates, airline offtakes and deliveries, a CORSIA-style credit ledger and ReFuelEU blending records. A React frontend shows dashboards for each. On first start it seeds about twelve months of mock data.

This is a monitoring and learning tool. Not legal advice. Regulatory values in it are editable defaults, and the README tells you to confirm them against the official texts. All figures in this post are what the repository itself outputs on its mock data. The repository is archived, so it will not be updated when rules change.

Who it is for

  • Students and analysts learning how SAF compliance data fits together
  • Teams prototyping an internal SAF tracking tool
  • Non-programmers who want an AI assistant to explain each calculation
Not for.
  • Real compliance reporting. Not legal advice, and the regulatory defaults may be out of date because the repository is archived.
  • Quoting its mandate, baseline or lifecycle values as current law. Check the official sources.
  • Treating the seeded numbers as real plant output. They are mock data.

Install

  1. Get the code (the repository is archived, so you can clone it but not push)
    git clone https://github.com/herrrickshaw/saf-monitoring-system.git
cd saf-monitoring-system/backend
  2. Create an environment and install
    python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

Quick start: commands and what you should see

Run the tests

pytest -q

39 passed.

Start the API (it seeds mock data on first run), then open the Swagger page

uvicorn app.main:app --port 8000

Interactive docs at http://localhost:8000/docs. The repo's run_app.sh also starts the React frontend on port 5173 (not run here).

Ask for the dashboard and the blending records

curl localhost:8000/api/dashboard/summary
curl localhost:8000/api/compliance/blending

JSON with totals and per-airport blending records.

Limits and honest caveats

  • Not legal advice. The README itself says to confirm all regulatory values against the current official texts before real compliance reporting.
  • Regulatory defaults (mandate shares, baselines, pathway limits, lifecycle values) are frozen at whatever the author entered, and the repository is archived, so they will not follow later changes. I did not verify any of them.
  • Everything the app shows on first start is seeded mock data, not real plant, airline or credit data.
  • SAF is not yet a notified sector under India's carbon market per the repository; its India module is a what-if tool, not an active scheme.
  • I ran the backend tests and API only. The React frontend and the PDF and Excel report paths were not run.
  • The tests print many datetime.utcnow deprecation warnings (73 warnings), which will become errors in future Python versions.
